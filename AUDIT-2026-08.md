## The through-line: verify with a control

The single most useful habit this audit established. Repeatedly, a check "passed" only
because it *couldn't fail*:

- The starship config check reported no unknown keys — until a deliberately invented
  `[zzz_not_a_module]` was also accepted, proving starship silently ignores unknown
  modules and the check had no power. Replaced with a comparison against
  `starship module --list`.
- A `yt-dlp` option scan flagged three valid options as unknown, because the regex
  required options to start a line and so missed every option with a short alias
  (`-c, --continue`).
- `grep -c` returning 1 on zero matches tripped `|| echo` fallbacks twice, printing
  bogus values.
- `ls a b` with one path missing tripped a `||` and reported "no config file anywhere"
  about a file that existed.
- `sudo -n docker images` couldn't authenticate, returned nothing, and got read as
  "zero images". True, but for the wrong reason — confirmed instead via
  `/var/lib/docker` being 0 bytes.

**Establish that a check can detect absence before trusting a negative result.**

## Findings that were real

### Silent breakage

- **`fix-wifi.sh` was load-bearing and untracked.** A hand-installed root hook cycling
  `ath11k_pci` around suspend; the Qualcomm QCNFA765 does not reliably re-associate
  without it. Owned by no package, absent from this repo — a fresh `install-root.sh`
  would have dropped it and left WiFi dead after every resume. Now tracked, both hooks
  installed by one idempotent loop.
- **`~/.local/bin/sioyek` was a 3-line wrapper, not the binary.** Forces
  `QT_QPA_PLATFORM=wayland`; without it sioyek falls back to XWayland. Also untracked.
- **rclone was failing silently.** No `OnFailure`, no retry ceiling. Now notifies via
  `notify-failure@` *and* appends to `~/.local/state/service-failures/failures.log` —
  a popup is useless if nobody is at the machine.
- **`install.sh` created the vim symlink before `~/.config` existed**, so a fresh machine
  failed at that step.
- **`xdg-user-dirs-update` clobbered the tracked `user-dirs.dirs` symlink** on a fresh
  login; the service is now masked.

### Config that never did anything

- **`gtk-3.0/settings.ini` and `gtk-4.0/settings.ini` were inert.** GTK appearance comes
  from dconf via the `xdg-desktop-portal` Settings interface, which overrides
  `settings.ini` for every key it serves. A commit intending `Noto Sans 11` had never
  taken effect — GTK apps render in `Adwaita Sans 11`. Both files removed; dconf
  documented as the real source.
- Vim's clipboard mappings never worked: the build is `-clipboard`, so `"+`/`"*` do not
  exist. Replaced with `\y`/`\P` piping to `wl-copy`/`wl-paste`.
- 7 dead tmux bindings, 7 invalid lazygit keys, 3 undefined git aliases, a `batt` awk
  divide-by-zero, `:ALEFix` erroring on every YAML/JSON save.

### Package-level

- **`aocl-gcc` (686 MiB) is load-bearing** despite `Required By: None` — C++ projects link
  `-lblas`/`-llapack`, which resolve to AOCL. Second-checked: libFLAME exports 12,161
  symbols with 0 of 30 common LAPACK routines missing; `dgemm`/`dgesv`/`dsyev` exact.
- **`PKG_CONFIG_PATH` must not be set globally.** AOCL's pkgconfig dir also holds
  `fftw3*.pc`, and pkg-config searches `PKG_CONFIG_PATH` *before* its compiled-in
  defaults — so exposing it makes `pkg-config fftw3` return AOCL's 3.3.10 while the
  system's 3.3.11 gets loaded at runtime (same soname). Per-project only.
- **Don't wrap BLAS calls in your own `omp parallel`.** `omp_max_active_levels` is 1 by
  default, so BLIS collapses to one thread inside an active region. Measured on
  4×1500³ dgemm: **435 GFLOP/s** letting BLIS thread vs **265** hand-parallelised over 4
  OpenMP threads. No oversubscription — just a 1.65× loss.
- `BLIS_NUM_THREADS` outranks `OMP_NUM_THREADS`, so setting the latter for your own
  parallel regions will not resize BLIS.
- **Tor Browser is deliberately unconfigured.** Its anonymity depends on every user
  looking identical, so a `user.js` or `userChrome.css` makes you *more* fingerprintable.
  Recorded in `CLAUDE.md` so a future audit doesn't offer to theme it.
- Removed: 370 MB orphaned `torbrowser-launcher` data, 15 MB unused fonts, ~7,000 lines of
  dead `zsh/archive` + `tmux/layouts/archive`.

## sioyek → papis → pask notes (new feature)

Built this session, both halves.

**Capture** (`dotfiles`): `Alt+n` → `bash/sioyek-papis-note` appends a page heading, the
selection, and sioyek's page/offset to the document's papis `notes.md`, then opens it in
nvim. The papis document is found from `%{file_path}`'s directory via
`papis edit --doc-folder`, and the note is created with `--notes --editor true` — a no-op
editor — so **papis writes the `notes:` key itself** and this repo never edits
`info.yaml`. Once the note exists both papis calls are skipped.

**Ingestion** (`papis-ask`, stage 4): notes are embedded with quotes stripped, cited as
`@ref (note)`, and chunked by `ask.chunk-chars`.

Three findings, each of which would have failed quietly:

1. **An uncommented capture is heading + quote.** Stripping quotes leaves `## p.3`, so the
   obvious implementation embeds a vector whose entire content is a page number — on every
   single capture. `indexable_prose()` skips a note unless some line is not a heading.
2. **The staleness gate read `chunk_source == "pypdf"`.** Notes are split by the same
   settings, so a `chunk-chars` change would have left every note chunked at whatever was
   configured the day it was written, with no mtime moving to reveal it.
3. **The `(note)` marker was overwritten and unread.** `update_index_metadata` lists
   `citation` in `fields_to_overwrite_from_metadata`, so the DocDetails upgrade replaced
   it with the papis title — and rendering never read `citation` anyway, building from
   `doc.other["ref"]`. A note cited as `[@Kalman_1960]`, identical to its paper. The marker
   now lives in `output.source_ref`. **Only live validation caught this**; no unit test
   looked at `citation`.

Why quotes are stripped: the passage is already embedded from the PDF, so indexing it
again makes one paragraph compete with itself for `ask.max-sources` — a question returns
two copies of it and one fewer other paper.

Sandbox: `~/learning/playground/sioyek-papis-notes/` — 17 checks, `PAPIS_LIB` isolation so
the real library is untouched, `bash run.sh --live` for the paid path.

## The nvim submodule, 2026-08-11/12

Audited after the fact (it was out of scope above). Same method, except merges are
fast-forward to match its near-linear history, and each finding also needs a submodule
pointer bump in `dotfiles`.

### The one that mattered: a latent data-loss path

`jupytext.nvim` had **never loaded since the initial commit**. Its trigger was
`ft = { "ipynb" }`, but Neovim detects `.ipynb` as **`json`**, so the filetype never
matched — and all of the plugin's wiring lives in `setup()` (no `plugin/` dir), so nothing
ran. Opening a notebook gave raw JSON.

The obvious fix — `lazy = false`, which is what its own README says — would have been **worse
than broken**:

- `commands.lua:4` builds a bare `"jupytext " .. file` and runs it through the shell. There
  is **no config option for the binary path**. Missing CLI → exit 127.
- `init.lua:88` reads `if vim.fn.filereadable(f) then`. That returns `0`/`1`, and **`0` is
  truthy in Lua**, so the read path continues *after* conversion failed. `readfile()` throws,
  the buffer is left empty, and the next `:w` writes it back.

Measured: a 933-byte, 3-cell notebook → **0 bytes**. So the broken `ft` trigger was the only
thing that had ever protected the notebooks. Two further inputs threw raw tracebacks once
armed — a notebook that does not exist yet (creating one: `utils.lua:16` calls
`io.open(f):read` with no nil check) and a malformed or 0-byte file.

Shape of the fix, and why each part: resolve the CLI **venv-first**
(`$VIRTUAL_ENV` → `<root>/.venv` → `PATH`) and call `setup()` **only** when something is
executable, because jupyter lives in per-project venvs here. Then harden the `BufReadCmd` —
and note that registering an earlier one **cannot** pre-empt the plugin's, because *all*
matching `BufReadCmd` autocommands run (verified). The callback has to be pulled out of
`nvim_get_autocmds`, deleted, and re-registered behind a readable check and a `pcall`. On
failure the raw file goes back into the buffer, because jupytext registers its `BufWriteCmd`
only after a *successful* read — leaving that buffer empty is what truncates the file. Two
traps in the wrapper: a truthy return **deletes** the autocmd, and a byte-exact "was it
damaged?" test needs a trailing-newline fixture or Neovim's own added newline hides the
difference between *untouched* and *truncated*.

### Silent breakage

- **`<leader>tc` was dead.** Upstream folded everything into subcommands of `:TSContext`, so
  the key raised a bare `E492` that nothing surfaced. Now calls `toggle()` directly — a
  module function cannot be renamed away as quietly as a command.
- **`nvim .` gave an empty buffer with no filetype.** `netrwPlugin` is disabled *and* oil set
  `default_file_explorer = true` while being lazy on `cmd`/`keys` — so oil's directory hijack,
  a `BufAdd` autocmd installed at `setup()` time (`oil/init.lua:1403`), did not exist when the
  buffer was added. Pressing `-` recovered it, which is why it went unnoticed. Cost of loading
  oil eagerly is **~1 ms**: the startuptime log says ~4.8 ms for oil + devicons, but devicons
  is not new work — lualine pulls it in at `VeryLazy` anyway.
- **Three filetypes were wrong**, all from `BufNewFile,BufRead` autocmds that ran *after*
  detection and overwrote it: `*alias*` is a **substring** glob, so `aliases.json` became
  `sh` instead of `json` and `my_aliases.md` became `sh` instead of `markdown`; `*.zsh` and
  `.zshrc` were forced from `zsh` to `sh`; and `.dvcignore` was mapped to `yaml` when DVC
  documents it as **gitignore** syntax.
- **jupytext's healthcheck threw** rather than reporting, calling `vim.health.report_start`
  (removed in Neovim 0.10). Now shadowed by `lua/jupytext/health.lua` in this repo, since an
  edit under `~/.local/share/nvim/lazy` is reverted by the next update.

### Config that never did anything

- **`vim.g.rcsv_align_mode = 0` is not a rainbow_csv option.** The plugin reads eight `g:`
  variables and documents fourteen; that name is in neither, nor anywhere in its tree. And
  there was nothing to disable: alignment is `:RainbowAlign`, a **command that rewrites the
  buffer** via `setline()`. So `CLAUDE.md`'s "alignment disabled by default for large file
  performance" was false twice over. `:RainbowShrink` is its inverse and is now bound.
- **twilight's 18-line theme-adaptive dimming block reduced to one number.** `expand` was
  unreachable (`view.lua:167` gates the whole treesitter branch on `options.treesitter`, set
  to `false`); the hex colours were never read (`config.colors()` walks `dimming.color` in
  order and stops at `"Normal"`); and the alpha was resolved once at load, so it never
  followed `<leader>th`. twilight already tracks theme changes through its own `ColorScheme`
  autocmd (`view.lua:20`).

### Redundant with modern Neovim

- **Five of eight filetype autocmds** duplicated Neovim 0.12, which already resolves `*.sh`,
  `Dockerfile*`, `*.toml`, `Pipfile`, `*.scala`, the dbt/DVC yaml names, and every `.env`
  form — the last to a purpose-built `env` filetype with its own syntax file. Replaced by one
  `vim.filetype.add()` declaring only what Neovim misses: **−84 lines**.
- **mini.bracketed was mostly shadowing built-ins.** Neovim 0.11+ ships `]b`/`[b`, `]d`/`[d`,
  `]q`/`[q` and `]l`/`[l`, so three of its four enabled modules re-implemented them and only
  `]f` was unique. Rebalanced to the four with no built-in equivalent: `]f`, `]i` (indent),
  `]x` (conflict), `]y` (yank history). Two of the *disabled* entries are load-bearing rather
  than tidying: `comment` would take `]c` from gitsigns' hunks, and `treesitter` would take
  `]t` from the built-in `:tnext`. The only thing given up is wrap-around — native `:cnext`
  stops at the last entry with `E553`.

### Gaps worth filling, found by looking rather than by breakage

- **Lua had no language server at all** — 22 files, ~5,300 lines, the language the config is
  written in. `lua_ls` is in the official repos. It immediately flagged three real
  LuaCATS bugs in `config/state.lua` (a comma in `@return string|nil value, or nil when…`
  parses as a *second* return whose type is `or`).
- **`*.py` sat in the format-on-save glob doing nothing.** basedpyright reports
  `textDocument/formatting = false`; a mangled file came back byte-identical after `:w`.
  `ruff` supplies the formatter, and the two are split by **which side carries the useful code
  action**, not by which is faster — see below.
- **Four parsers were installed but undeclared** (`asm`, `ini`, `kdl`, `bibtex`), so they
  worked here and would vanish on a fresh machine, silently. `kdl` serves `niri/config.kdl`,
  `ini` serves `foot.ini`/`fuzzel.ini`, `bibtex` serves papis' `refs.bib`. A fifth,
  `zathurarc`, is an orphan upstream no longer ships.
- **Correcting `*.zsh` to `ft=zsh` would have removed folding**, because `foldexpr` and the
  textobject queries need a parser and none was installed. nvim-treesitter *does* ship a zsh
  grammar; it beats the bash parser on zsh-only syntax (0 vs 1 error on
  `print -l ${(f)arr}`). No `language.register` shim needed.
- **Spell checking was on for `tex` only.** Now markdown and typst too, free — `en.utf-8.spl`
  ships with Neovim — and quiet, because `spelloptions` defaults to `noplainbuffer`, which
  makes spell obey treesitter's `@nospell`. Plus a tracked 453-word technical list.

### The Python split, because it is easy to get backwards

`ruff` and `basedpyright` both report unused imports, unused variables and undefined names.
De-duplicating by silencing basedpyright looks obvious and is **wrong for one of them**:
auto-import (`import json`) hangs off `reportUndefinedVariable`, so turning it off left
**zero** code actions on an undefined name. Ownership therefore follows the action:

| Diagnostic | Owner | Why |
|---|---|---|
| unused import / unused variable | ruff | its quickfix removes them; basedpyright adds nothing |
| **undefined name** | **basedpyright** | its diagnostic carries auto-import; `F821` is in ruff's `ignore` |
| types, completion, hover, navigation | basedpyright | ruff has **no type system at all** |
| formatting | ruff | basedpyright cannot; manual via `<leader>cf`, `*.py` stays out of the save glob |

Two ruff mechanics that cost time: its settings must go in **`init_options.settings`** —
under `settings` they are **silently ignored** — and its defaults are broader than the usual
shorthand suggests, also raising `I001` (isort) and `B018` (bugbear).

### Checked and dropped — not problems

Recorded so they are not re-investigated: `loaded_python3_provider = 0` does **not** break
rainbow_csv's RBQL (`rainbow_csv.vim:1689` tries an external `python3` *before*
`has("python3")`); KaTeX `0.17.0` in `md_preview` is a real version (latest is 0.18.4);
`bashls` on zsh files emits **no** bogus diagnostics, because shellcheck refuses zsh outright
rather than mis-linting it (control: a `.sh` file with a known issue does report `SC2086`);
systemd units get `ft=systemd` by **path**, so `dotfiles/systemd/user/*.service` is fine; and
gitsigns' `]c` is fine — it attaches asynchronously, which reads as "NOT MAPPED" if you do
not wait.

### The through-line held, and found new ways to fail

The habit from the first audit kept paying, and three new shapes of powerless check turned up:

- **`--headless` never fires `VeryLazy`.** This invalidates the "healthy baseline" recorded
  in the *Not audited* section below: only **5 of 37 plugins** were loaded when that
  `:checkhealth` ran. Force-loading everything surfaced a deprecation — in jupytext.
  It also silently broke a bracket-mapping test into measuring Neovim's defaults, and made a
  startup benchmark overstate oil's cost ~4×.
- **A sandbox can invalidate its own premise.** Adding a `.venv` to the jupytext sandbox made
  every "no jupytext anywhere" check quietly test the opposite; two started failing. They now
  run from `mktemp -d` and the harness **asserts** nothing resolves there first. Separately,
  `run.sh` shared `work/` with the manual scenarios and deleted their fixtures.
- **Isolated-string checks.** `spellbadword("word")` ignores buffer context, so it "flagged"
  code that `]s` correctly skips. `pcall` around `nvim_feedkeys` catches nothing, so an error
  counter read `0` for a mapping that was demonstrably broken. And an extmark count was
  identical for the old and new twilight config, so it distinguished nothing.

An unconditional `echo` was also presented as a measurement again — the same trap as the
`snapper` line in the first audit.

- **Reported `\mathbf` flagged 648× as though the spell config were at fault.** It is the

- **Wrote step-by-step scenarios that were wrong about which directory to run in**, so

- Twice bumped the submodule pointer with `git add nvim` **from inside the submodule**, where
  that path does not exist.
