# Fixture: the 2026-09-02 suspend storm

The reference case for this skill: a known failure with a known answer, distilled from the
journal on **2026-09-06** while it was still retained.

**Why this file exists.** `journald` here is capped at `SystemMaxUse=200M` and was at 177.8 MB
with the oldest entry at 2026-07-19 — a window of roughly 49 days. The raw journal for this
incident rotates out around **2026-10-21**. The queries below stop returning anything after
that; the numbers and the two shapes do not.

**Why it is distilled rather than captured.** The full `systemd-suspend.service` excerpt for the
window is 4104 lines / 454 KB, and 456 of those cycles are byte-identical apart from timestamps
and PIDs. One cycle of each kind carries everything the diagnosis needs.

## The numbers, counted per boot

The storm is boot `-13` (as indexed on 2026-09-06; boot indices shift with every reboot, so
select it by date, not by that number).

| Query on that boot | Count |
|---|---|
| `Starting System Suspend` | **460** |
| `Failed to freeze unit` | **456** |
| `System returned from sleep` | **4** |

460 = 456 + 4. Every stage line of a failed cycle appears exactly 456 times.

```bash
b=-13   # find it by date: journalctl --list-boots
for p in 'Starting System Suspend' 'Failed to freeze unit' 'System returned from sleep'; do
  printf '%-30s %s\n' "$p" \
    "$(journalctl -b "$b" -u systemd-suspend.service --no-pager | grep -c "$p")"
done
```

**This is where a documented number was found wrong.** `CLAUDE.md` read *"916 suspend attempts,
456 hard aborts"* until 2026-09-06. 916 is `Starting System Suspend` + `Failed to freeze unit`
summed — both are logged once per attempt, so it is a doubled count, not an attempt count. The
correction is in `CLAUDE.md`. The lesson is the skill's third step: **count per boot, and know
which line you are counting.**

Still unresolved, deliberately: `CLAUDE.md` also cites **1831 wifi disconnects**. A pattern
written on 2026-09-06 returns 910 for that boot, but it is *a different pattern from the one
that produced 1831* and there is no record of the original. A number from a probe you did not
write is not evidence against a number from a probe you cannot see. Left alone.

## Shape 1 — a healthy cycle

Six lines, fixed order (observed on boot `-2`, 2026-09-04):

```
systemd[1]:       Starting System Suspend...
systemd-sleep[…]: Successfully froze unit 'user.slice'.
systemd-sleep[…]: Performing sleep operation 'suspend'...
systemd-sleep[…]: System returned from sleep operation 'suspend'.
systemd-sleep[…]: Successfully thawed unit 'user.slice'.
systemd[1]:       systemd-suspend.service: Deactivated successfully.
```

## Shape 2 — a failed cycle

```
systemd-sleep[…]: Failed to freeze unit 'user.slice': Connection timed out
systemd-sleep[…]: Performing sleep operation 'suspend'...
systemd-sleep[…]: Failed to put system to sleep. System resumed again: Device or resource busy
systemd-sleep[…]: Successfully thawed unit 'user.slice'.
systemd[1]:       systemd-suspend.service: Main process exited, code=exited, status=1/FAILURE
systemd[1]:       systemd-suspend.service: Failed with result 'exit-code'.
systemd[1]:       Failed to start System Suspend.
systemd[1]:       systemd-suspend.service: Consumed 3.516s CPU time over 1min 41.743s wall clock
systemd[1]:       Starting System Suspend...          <-- the retry, immediately
```

## What the two shapes teach, and the trap in comparing them

**A stage fails by substitution, not by absence.** Line 2 is not missing from the failed cycle —
it is *replaced*, by `Failed to freeze unit 'user.slice': Connection timed out`. Diagnosing by
"which line is absent" would miss it.

**The freeze failure is not fatal to the sequence.** systemd logs it and attempts the suspend
anyway; the abort happens one line later, in the kernel, as `Device or resource busy` (`EBUSY`).
Two different failures are visible in one cycle and only the second one stops anything.

**Only `System returned from sleep operation` proves the machine actually slept.** It appears 4
times in a boot with 460 attempts. Its absence, not the presence of an error, is what says the
night was lost.

**The retry is immediate and unbounded.** `Consumed … over 1min 41.743s wall clock` is the
~100 s that `CLAUDE.md` describes as a retry interval — it is the duration of one failed
attempt, not a delay between attempts. With the lid shut this repeats forever.
